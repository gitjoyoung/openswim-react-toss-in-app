# 앱인토스 제약 정리 (실수 방지용)

출처: 앱인토스 개발자센터. 링크 인덱스는 `apps-in-toss.md`.
이 문서는 **검수에서 걸리는 것**과 **우리가 실제로 틀렸던 것**만 적는다.

---

## 1. 뒤로가기

**규칙: 토스 네비게이션 바의 뒤로가기와 미니앱 자체 뒤로가기 버튼이 동시에 보이면 안 된다.**
자체 버튼 자체가 금지는 아니다. 동시 노출이 금지다. 비게임 출시 체크리스트의 명시 항목.

- 뒤로가기는 모든 화면에서 동작해야 한다.
- 최초 화면에서 뒤로가기를 누르면 미니앱이 종료돼야 한다.
- 안드로이드 시스템 백버튼도 뒤로가기 또는 종료로 동작해야 한다.

**우리 구현 (2026-09-05 기준)**
- 상세 히어로에 있던 자체 뒤로가기 버튼은 **제거했다.** 토스 네비게이션 바 뒤로가기와 중복이었다.
- 뒤로가기 처리는 `src/hooks/useAppNavigation.ts`의 `graniteEvent` `backEvent` 리스너 하나로 모은다.
  상세가 열려 있으면 상세만 닫고, 첫 화면이면 `Screen.close()`로 미니앱을 종료한다.
- 상세를 닫는 다른 경로: 하단 탭바 탭(`changeTab`), 데스크톱 좌우 여백 클릭.
- 일반 브라우저(localhost 미리보기)에는 네이티브 back 브리지가 없어 상세를 닫을 수 없다. 탭바로 나간다.

출처: <https://developers-apps-in-toss.toss.im/checklist/app-nongame.md>

## 2. 인앱 배너 광고

### 금지 (위반 시 광고 노출 제한)

**오클릭 유도**
- 광고와 콘텐츠 구분이 불명확한 배치
- 광고 위장(예: "추천 서비스"), 가이드 외 색상·글꼴 변경, 타이틀/라벨/CTA 임의 수정
- 버튼 등 사용자 상호작용 요소와 인접 배치
- 서비스 CTA와 구분이 어렵거나, 서비스 CTA를 인지·접근하기 어렵게 만드는 구성

**중복 노출**
- **동일 화면에 동일 포맷 광고 2개 이상**
- 광고 영역 주기적 Refresh, 클릭·노출 성과 인위적 발생

**가려진 광고**
- 투명 광고, 다른 카드 UI 뒤에 광고 DOM 삽입
- 노출 상태가 명확히 확인 가능해야 한다

### 출시 체크리스트 항목
- 인트로/로딩/컷신/**팝업 모달** 등 일시적 화면에 노출 금지
- **스크롤 가능한 화면에만** 노출
- 배너는 상단/중앙/하단 중 적절한 위치
- 사용자가 예상하기 어려운 순간에 노출 금지

### 우리 구현
- 광고 그룹을 자리별로 분리한다: `VITE_TOSS_AD_GROUP_ID`(홈), `VITE_TOSS_AD_GROUP_ID_DETAIL`(상세).
- **상세 시트가 열리면 홈 광고를 언마운트한다** (`App.tsx`의 `showAd={!selected}`).
  안 내리면 가려진 광고가 노출로 잡히고, 상세 광고와 겹쳐 "동일 화면 동일 포맷 2개"에 걸린다.
- 홈은 필터 칩 아래, 상세는 시간표 아래·요금 위. 둘 다 버튼과 떨어뜨린다.
- 상세는 `separated` 옵션으로 위아래 `Divider`를 둘러 독립 영역을 만든다.
  구분선은 **광고가 실제 렌더된 뒤에만** 붙인다(`onAdRendered`). `onNoFill`이면 빈 띠가 남는다.
- **패딩을 주지 않는다.** `variant: "card"` 소재가 자체 여백과 라운드를 갖고 있어
  우리가 패딩을 더하면 이중으로 들어가 떠 보인다. (실기기 확인, 2026-09-05)

> 확인 필요: 상세 화면은 `position: fixed` 오버레이 시트다. 스크롤은 되지만
> 검수자가 "팝업 모달"로 판단할 여지가 있다. 반려되면 상세 광고부터 검토한다.

출처: <https://developers-apps-in-toss.toss.im/documentation/common/monetization/iaa/web-banner.md#policy>

## 3. Safe Area

**`env(safe-area-inset-top)`은 웹뷰 위치와 무관하게 기기값(노치 47~59px)을 반환한다.**
미니앱 콘텐츠는 이미 토스 네비게이션 바 아래에서 시작하므로 상단 인셋을 더할 자리가 없다.

- 화면 최상단이 아닌 **요소 내부 좌표에는 세이프에어리어를 쓰지 않는다.** 상수를 쓴다.
- 하단은 `SAFE_BOTTOM`(`src/design/tokens.ts`)을 쓴다.
  `max(var(--toss-safe-area-bottom, 0px), env(safe-area-inset-bottom), 20px)` — 토스 웹뷰 변수 우선.
- `calc(8px + env(...))`처럼 **더하지 않는다.** `max()`도 큰 값을 고르므로 인셋이 있으면 여전히 밀린다.

**실패 사례 (2026-09-05)**: 상세 뒤로가기 버튼이 `calc(8px + env(safe-area-inset-top))`이라
노치 기기에서 67px 아래에 놓였다. `max(12px, env(...))`로 바꿨지만 여전히 59px 밀렸다.
로컬 브라우저는 `env()`가 0이라 두 번 다 재현되지 않았다. **세이프에어리어 수정은 실기기에서만 검증된다.**

## 4. 기타 검수 항목

- 지도처럼 꼭 필요한 경우를 제외하고 **제스처 확대·축소 비활성화**.
  iOS 웹뷰는 `user-scalable=no`를 무시하므로 `App.tsx`에서 `gesturestart` 등을 직접 막는다.
  지도는 `data-allow-zoom`으로 예외.
- **라이트 모드**로 구현.
- 스크롤·터치·화면 전환 반응이 2초 이상 지연되지 않아야 한다.
- 링크나 컴포넌트로 **자사 서비스 이동이나 자사 앱 설치를 유도하지 않는다.**
- TDS Mobile(`@toss/tds-mobile`) 사용.

## 5. 권한

`apps-in-toss.config.ts`의 `permissions`에 선언해야 실기기에서 동작한다.

| 권한 | 용도 |
|---|---|
| `geolocation` / `access` | 내 위치 기준 정렬, 지도 현재 위치 |
| `clipboard` / `write` | 상세 주소 복사 버튼 (`Clipboard.setText`) |

권한을 새로 추가하면 검수에서 용도를 본다. 실제 쓰는 것만 넣는다.

## 6. 토스쇼핑 쉐어링크

- 허용 사례: 각 제품을 소개·추천한 뒤 최저가 구매 플랫폼으로 이동.
- **공정위 고지 문구를 상품 목록 바로 위에 유지한다** (`GEAR_DISCLOSURE`).
- 본인 구매는 수익으로 집계되지 않는다. 테스트할 때 실제 구매하지 않는다.
- 판매가·쿠폰가는 자주 바뀌므로 앱에 하드코딩하지 않는다. 제목과 이미지만 쓴다.
- 상품은 Neon `public.gear_items`에 URL만 넣고 `pnpm gear:sync`로 OG 제목/이미지를 채운다.
  클라이언트에서 `toss.im` HTML을 직접 fetch하면 CORS로 실패한다.

## 7. 배포·검수

```
pnpm test && pnpm build          # openswim.ait + deploymentId 생성
bundle_upload → PUT → bundle_upload_complete → bundle_build_status
bundle_test_push                 # 실기기 확인
bundle_submit_review             # 사용자 확인 후
```

- **검수를 취소하면 그 deployment는 영구히 재신청할 수 없다.** 번들을 새로 만들어야 한다.
- 검수 승인 ≠ 배포. 승인 후 출시 단계가 따로 있다.
- 실기기에서만 확인되는 것: 광고 실제 노출, 세이프에어리어, 권한 팝업, 클립보드.
  로컬 브라우저에는 광고 브릿지도 back 브릿지도 없다.

### 환경 제약
- 개발 서버는 반드시 `http://localhost:5173`. 카카오맵에 등록된 도메인이라
  `127.0.0.1`이나 다른 포트는 지도가 안 뜬다. `vite.config.ts`에 `strictPort: true`로 고정.
- 콘솔 MCP는 OAuth 콜백을 `localhost:33418`로 받는다. Aside 샌드박스에서는
  로컬 서버 프로세스가 툴 호출 사이에 종료되고 브라우저 실행도 막혀 있어 자주 실패한다.
  실패하면 빌드만 하고 업로드는 사람이 콘솔에서 직접 하는 게 빠르다.
- `ait deploy` CLI는 콘솔 API 키가 있어야 한다. 키는 **워크스페이스 > 연동 > 콘솔 API 키**에서 발급한다.
  발급할 때 접근할 앱을 고르므로(전체 앱 / 특정 앱), **그 앱을 만들기 전에 발급한 키로는 배포할 수 없다.**
  - 2026-09-10 해결: 워크스페이스 57209에 콘솔 API 키가 아예 없었다.
    `~/.ait/credentials`에 있던 키는 2026-06-19 발급분으로, 프로젝트 첫 커밋(2026-07-07)보다 3주 빨랐다.
    즉 다른 워크스페이스/앱의 키였고, 그래서 인증은 통과하는데 앱 접근만 막혔다.
  - **4031 은 원인을 알려주지 않는다.** "앱이 없거나 앱 정보에 접근할 수 있는 권한이 없어요" 하나로
    앱 없음과 권한 없음을 모두 덮는다. 존재하지 않는 앱 이름을 넣어도 같은 응답이 온다.
  - 키가 죽었는지 앱 권한이 없는지 가르는 법: 배포 API를 직접 찔러 HTTP 상태를 본다.
    ```
    POST https://apps-in-toss.toss.im/console/api-public/v3/openapi/bundles/<appName>/upload-start
    Authorization: Bearer <apiKey>
    ```
    - HTTP 403 (본문 없음) → 키 자체가 거부됨. 만료·오타·폐기.
    - HTTP 200 + `errorCode 4031` → 키는 유효하나 그 앱에 대한 권한이 없음. 키를 다시 발급한다.
    - HTTP 200 + `resultType SUCCESS` → 권한 정상.
  - 새 키 등록: `npx ait token add default --api-key <키>`. 키는 발급 화면에서 한 번만 보여준다.
